# Building and Releasing Desktop Apps

This guide is for project maintainers. Normal users should download a published application as described in the [Installation Guide](01-installation.md).

## macOS Release Configuration

The prototype release is an ad-hoc-signed Apple Silicon application for macOS 14 or later. It is not signed with an Apple Developer ID and is not notarized. PyInstaller bundles the Python runtime, Tcl/Tk, Pillow, FFmpeg, and ffprobe into `Trivia Countdown.app`.

FFmpeg is built with `libx264`, so the bundled FFmpeg executables are GPL software. Every release must include the corresponding source archive generated by the build and must retain [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md).

## Build the macOS App Locally

The build requires an Apple Silicon Mac, the Xcode Command Line Tools, `uv`, `git`, `make`, and `pkg-config`. The repository's `.python-version` selects Python 3.12 for local uv commands; CI pins the application, FFmpeg, x264, Python 3.12.10, and PyInstaller versions. Compiler and filesystem metadata can still vary between runner images. Builds are repeatable from exact sources, not guaranteed byte-for-byte reproducible.

Build the pinned FFmpeg and x264 sources:

```sh
scripts/build_ffmpeg_macos.sh
```

Build the app and DMG:

```sh
scripts/build_macos_dmg.sh
```

Generated artifacts are written to `dist/`:

- `Trivia-Countdown-<version>-macOS-arm64.dmg`
- `Trivia-Countdown-FFmpeg-<ffmpeg-version>-sources.tar.gz`
- `SHA256SUMS`

The app bundle is also left at `dist/Trivia Countdown.app` for local testing. Build outputs are ignored by Git.

## Verify the macOS Build

Run the normal checks and inspect the app signature:

```sh
uv run python -m compileall -q make_trivia_countdown.py make_trivia_countdown_gui.py trivia_countdown
uv run python -m unittest discover -s tests
uv run python make_trivia_countdown.py --help
codesign --verify --deep --strict --verbose=2 "dist/Trivia Countdown.app"
hdiutil verify "dist/Trivia-Countdown-0.1.1-macOS-arm64.dmg"
git diff --check
```

Before publishing, download the DMG through a browser and test it on a clean macOS 14 or later Apple Silicon account. This exercises the same quarantine and **Open Anyway** workflow that users encounter.

## Build the macOS App With GitHub Actions

Open the repository's **Actions** tab, select **Build unsigned macOS DMG**, and choose **Run workflow**. A successful run provides a `trivia-countdown-macos-arm64` workflow artifact containing the DMG, corresponding GPL sources, and checksums. The workflow also publishes GitHub build provenance attestations. A manual run from a branch does not create a GitHub release; one dispatched from a matching `v`-prefixed tag creates or updates that tag's draft prerelease.

### Verify the Microsoft Store automation connection

The manually triggered **Verify Microsoft Store connection** workflow checks
that the Store credentials are configured in GitHub Actions and makes a
read-only request for the reserved Trivia Countdown product. It does not upload,
submit, or publish an app. Configure the repository secrets
`AZURE_AD_APPLICATION_CLIENT_ID`, `AZURE_AD_APPLICATION_SECRET`,
`AZURE_AD_TENANT_ID`, and `SELLER_ID` before running it. The first Store
submission must still be created and published through Partner Center; Microsoft
Store CLI submission automation is for updates after first publication.

## Prepare a macOS GitHub Release

1. Update the version in `pyproject.toml` and regenerate `uv.lock` with `uv lock`.
2. Commit and push the release changes.
3. Create and push a new `v`-prefixed tag that exactly matches the project version, such as `v0.1.1` for version `0.1.1`. Do not reuse published `v0.1.0`.
4. Wait for **Build unsigned macOS DMG** to finish.
5. Open **Releases** on GitHub and inspect the draft prerelease created by the workflow.
6. Download and test the attached DMG, source archive, and checksums.
7. Add any user-facing caveats to the generated release notes, then publish the prerelease.

Example tag commands:

```sh
git tag v0.1.1
git push origin v0.1.1
```

Do not publish a DMG without its matching FFmpeg/x264 source archive and `SHA256SUMS` file.

The release workflow is retry-safe while a release remains a draft: a rerun replaces its attached assets. It refuses to alter assets after publication. Users can verify provenance with `gh attestation verify <artifact> --repo princeendo/trivia_countdown` before using the **Open Anyway** override.

## Windows Preview Build

The Windows preview targets Windows 10 22H2 and Windows 11 on x64 hardware. It uses a per-user, unsigned Inno Setup 7.1.0 installer and bundles a PyInstaller GUI application, Noto Sans fonts, and FFmpeg 9.0.1 executables built from pinned FFmpeg, x264, and zlib sources. End users do not install FFmpeg separately. External-library autodetection is disabled, avoiding the former supplier bundle's large dependency/source closure. Built-in input decoders/demuxers remain enabled; optional external codecs such as libaom/libdav1d AV1 decoding are not included.

Build it on Windows in PowerShell after installing Python with Tcl/Tk, uv, Git, and Inno Setup 7.1.0. Use a checkout path without spaces or apostrophes for the native compiler work tree (rendered video paths have no such restriction). Set up the isolated MSYS2 UCRT64 compiler tools once, then build:

```powershell
.\scripts\setup_windows_ffmpeg_tools.ps1
.\scripts\build_windows_installer.ps1
```

The setup helper downloads and hash-verifies a pinned MSYS2 self-extracting base into `build\tools\msys64`, updates that isolated installation, and installs its compiler/build tools without changing system `PATH`. It uses the upstream CI self-extractor because Windows Server 2022's `tar.exe` stalled on the equivalent `.tar.xz` archive. The installer build fetches exact Git commits, compiles FFmpeg/x264/zlib, audits native x64 executable imports against a Windows-system-DLL allowlist, creates the multi-resolution icon, collects runtime license files, builds `dist\Trivia Countdown\`, verifies the frozen application's preview and render paths, and writes these release candidates:

- `Trivia-Countdown-<version>-Windows-x64-Setup.exe`
- `Trivia-Countdown-FFmpeg-9.0.1-Windows-x64-sources.tar.gz`
- `Trivia-Countdown-<version>-Windows-x64-SHA256SUMS.txt`

Toolchain setup logs download, checksum, extraction, initial shell setup, and
package-update phases separately. The base download has a five-minute timeout;
CI limits the complete setup step to 20 minutes. If setup stalls, use the last
logged phase to diagnose it before retrying. Initial shell setup initializes
the MSYS2 keyring before package updates, following the
[MSYS2 CI instructions](https://www.msys2.org/docs/ci/#other-systems).

To build just FFmpeg and its source archive, run `.\scripts\build_ffmpeg_windows.ps1`. The source trees and compile script are archived together with revision URLs, configuration and DLL-import reports, toolchain package versions, and licenses. Hash-verified binaries and sources can be reused while their build inputs are unchanged; pass `-Force` to rebuild. A custom MSYS2 installation can be selected with `-Msys2Root 'C:\msys64'` on the FFmpeg build, installer build, or path verifier. `fetch_windows_ffmpeg.ps1` is retained only as a compatibility entry point to the source build; it no longer downloads Gyan binaries. The source archive includes [rebuild instructions](../packaging/FFMPEG_WINDOWS_SOURCE_README.md). These builds are source-pinned, not promised byte-for-byte reproducible across toolchain updates.

The **Build unsigned Windows installer** workflow first runs source compilation, all discovered tests under `tests/`, and CLI help, then sets up the compiler, repeats the build, verifies checksums for both the installer and source archive, and publishes GitHub build provenance for the installer, source archive, and checksum file. Native-command failures stop the build instead of allowing stale artifacts to pass. The Inno Setup installer hash is published in the immutable [Inno Setup 7.1.0 release](https://github.com/jrsoftware/issrc/releases/tag/is-7_1_0).

After building, the workflow reruns the full test suite with the newly bundled FFmpeg tools on `PATH`, including a real execution of the source GUI's generated PowerShell command. UNC and long-path cases still require the dedicated configured path verifier below. macOS package CI also discovers the full suite before and after building its media tools.

The installer rejects older Windows releases and non-x64 operating systems, uses the multi-resolution application icon, and installs `Sample Trivia Questions.csv` beside the executable. Application runtime resources and third-party notices remain under `_internal/`.

### Prepare the Windows draft prerelease

A manual workflow run from a branch produces verified workflow artifacts, **not** a release. After qualification, update the project version and lockfile, commit/push, and create a new matching `v`-prefixed tag. A tag run creates or updates a **draft prerelease** containing the three Windows release files. Windows and macOS draft updates are serialized for the tag so simultaneous builds do not race to create the release. Reruns replace only their platform's draft assets; both workflows refuse to change any published release. Do not reuse the already published `v0.1.0` tag.

GitHub wraps the `trivia-countdown-windows-x64` workflow artifact in a ZIP for
download. Testers must extract it and launch the included
`Trivia-Countdown-<version>-Windows-x64-Setup.exe` installer. Do not distribute
the intermediate `dist\Trivia Countdown\` directory as an installer; its
`Trivia Countdown.exe` launches the app directly. Published release assets
provide the **Setup.exe** as a direct download after qualification.

Before publishing, complete and retain the [Windows preview qualification checklist](../tasks/windows_preview_qualification.md). This includes human source/license approval, separate-machine testing, every DPI setting, a version-changing upgrade, and browser-download verification. CI completion never publishes a Windows release automatically. If a separate test system is unavailable, keep the candidate unpublished and the checklist pending.

### Verify the frozen Windows application

The installer build automatically runs this check before invoking Inno Setup. To repeat it against an existing PyInstaller build or an installed application:

```powershell
.\scripts\verify_windows_package.ps1
.\scripts\verify_windows_package.ps1 -ApplicationDirectory 'C:\Users\YourName\AppData\Local\Programs\Trivia Countdown'
```

The verifier removes Python and FFmpeg from the child process's `PATH`, clears `PYTHONHOME` and `PYTHONPATH`, launches the windowed application from outside the source directory, and explicitly waits for its exit code. It constructs the GUI, checks bundled tool versions, extracts previews, and performs two short renders (with and without audio) using paths with spaces, Unicode, and apostrophes. It checks H.264 video, 640x360 dimensions, three-second duration, optional AAC audio, and complete output decoding. Synthetic videos are deleted after the check; timestamped JSON reports remain under `build\verification\WIN-405-*.json`. The workflow uploads these as `windows-package-verification`, including failure reports when available. The default timeout is 180 seconds; use `-TimeoutSeconds` to adjust it up to 3600 on slower machines.

Internally, `TRIVIA_COUNTDOWN_SMOKE_TEST=render` selects these checks and requires an absolute `TRIVIA_COUNTDOWN_SMOKE_REPORT` path whose parent directory exists. The existing `TRIVIA_COUNTDOWN_SMOKE_TEST=1` startup-only mode remains available and unchanged. Neither mode replaces manual confirmation of child-console behavior, installed icons and shortcuts, DPI layout, cancellation, or installer qualification.

### Verify the Windows path matrix

Before qualifying the source render path, run the WIN-302 verifier from a Windows PowerShell session in the repository root. Supply a writable UNC share and a writable local directory on a system with Windows long paths enabled:

```powershell
.\scripts\verify_win302.ps1 -UncTestRoot '\\server\share\trivia-countdown-win302' -LongPathTestRoot 'C:\trivia-countdown-win302'
```

The script builds or verifies the cached source-built FFmpeg tools, requires all configured path tests to execute rather than skip, and writes a timestamped report under `build\verification\`. It restores the caller's `PATH`, temporary-directory variables, and test-root variables on exit, including failure. Set up the compiler first if no verified build is available. Run source sync/checks and package builds sequentially: source-only `uv sync --frozen` removes the build dependencies from the shared environment. Retain the report with the Windows version and test-root details as WIN-302 verification evidence. Earlier Gyan-build qualification does not qualify these replacement executables.

Before publishing, review and attach the matching Windows source archive with its build script, instructions, licenses, and notices. The self-built Windows media executables use GPLv2-or-later; the former supplier's GPLv3 build and the macOS source archive are not substitutes. Verify the installer and source archive checksums and run `gh attestation verify <artifact> --repo princeendo/trivia_countdown` for each artifact after CI. A local source build does not establish CI provenance or complete release qualification.

Then install the release candidate on a separate live Windows 10 22H2 or Windows 11 x64 system and complete the install, launch, render, playback, upgrade, uninstall, and icon checks. VM images and pristine-system qualification are not required. Document Microsoft Defender SmartScreen accurately: it may warn because the installer is unsigned and has little reputation. Direct users to verify the release checksum and provenance; never advise disabling SmartScreen or Windows security controls.

The selected candidate is app **0.1.1**, Git tag **v0.1.1** when ready, and Store

The Store product is `9PBDS94C8XD0`; its manifest uses

`CN=49A512EA-D5D6-441A-8499-B44017F81C7D`, and publisher display name `Colin White`.
These were supplied from Partner Center; compare against the current Product

### Version policy

`[project].version` remains the app/release version. The
`[tool.trivia-countdown.windows-store]` table in `pyproject.toml` explicitly pairs
`app-version` with an independent, increasing `package-version`. The packager
rejects a stale pairing. Microsoft requires four integer components, a nonzero
first component, and a fourth component of zero reserved for Store use; thus
`0.1.1.0` is not the chosen Store version. A Store package starting with `1` does
not promote the app to stable 1.0.

For each Store update, choose a package version greater than every previously
distributed package for this identity/architecture, update the app-version
pairing, and regenerate `uv.lock` when the app version changes. Increment one of
the first three Store components for a changed candidate used in upgrade tests;
do not use the fourth component as a CI build counter. Unpublished builds can
be rebuilt, but retain the exact hash/commit for every tested/submitted candidate.

### Build and inspect the MSIX

Use Windows x64 with Python 3.12, the existing Windows build prerequisites, and
the Windows 10/11 SDK's x64 **MakeAppx.exe**. The Windows CI image supplies the SDK;
the script selects the newest installed version numerically, or accepts an
explicit `-MakeAppxPath`. Its selected executable path appears in build output;
retain the SDK version with qualification evidence.

```powershell
.\scripts\setup_windows_ffmpeg_tools.ps1
.\scripts\build_windows_installer.ps1
.\scripts\build_windows_msix.ps1
```

The last command reuses the current frozen app; it does not invoke Inno Setup.
Rebuild that app after changing code, notices, samples, or version metadata. The
packager checks embedded project metadata and pairs the bundled FFmpeg/ffprobe
and source archive hashes against the native build manifest. It stages the app
under `build\windows\msix\app`, adds the manifest and generated base-size PNGs,
and reruns the frozen preview/audio/silent-render checks there. MakeAppx schema
and semantic validation remain enabled. A Python inspection compares every
staged payload byte against the MSIX and writes
`build\verification\STORE-002-msix.json`. This is structure/payload evidence,
not an installed-package or certification result.

Generated Store artifacts are:

- `Trivia-Countdown-1.0.1.0-Windows-x64.msix` (unsigned for Store upload)
- `Trivia-Countdown-1.0.1.0-Windows-x64-MSIX-SHA256SUMS.txt`
- The same matching `Trivia-Countdown-FFmpeg-9.0.1-Windows-x64-sources.tar.gz`
  used for the EXE candidate

The **Build unsigned Windows installer** workflow is configured to upload these
as **trivia-countdown-windows-store-x64**, separately from the EXE artifact.
It attests the MSIX and MSIX checksum file; the existing Windows attestation
covers the shared source archive. **windows-msix-verification** contains
structure and staged frozen reports. The first Windows run of this new path
remains pending until recorded in the tracker. The MSIX remains a workflow
artifact: the tag release job downloads only the EXE artifact, and does not
publish the MSIX or submit anything to Partner Center. CI does not install the
MSIX or run WACK on its Windows Server runner.

### Local MSIX installation and verification

Use a supported Windows 10 22H2 or Windows 11 x64 test machine and an account
with no existing Trivia Countdown MSIX. Keep the original unsigned MSIX and its
checksums unchanged for Partner Center. On the test machine, copy it into an
ignored `build\msix-local-test` directory, then sign **the copy** with a temporary
self-signed code-signing certificate. In Windows PowerShell 5.1, from the repo:

```powershell
$testRoot = New-Item -ItemType Directory -Force 'build\msix-local-test'
$testPackage = Join-Path $testRoot.FullName 'Trivia-Countdown-local-test.msix'
Copy-Item -LiteralPath 'dist\Trivia-Countdown-1.0.1.0-Windows-x64.msix' -Destination $testPackage
$cert = New-SelfSignedCertificate -Type Custom -Subject 'CN=49A512EA-D5D6-441A-8499-B44017F81C7D' -FriendlyName 'Trivia Countdown local MSIX test' -CertStoreLocation 'Cert:\CurrentUser\My' -KeyUsage DigitalSignature -KeyAlgorithm RSA -KeyLength 2048 -HashAlgorithm SHA256 -NotAfter (Get-Date).AddDays(7) -TextExtension @('2.5.29.37={text}1.3.6.1.5.5.7.3.3', '2.5.29.19={text}')
$cerPath = Join-Path $testRoot.FullName 'TriviaCountdown-local-test.cer'
Export-Certificate -Cert $cert -FilePath $cerPath
# Replace this path with the installed SDK version used for the package build.
$signTool = 'C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64\signtool.exe'
& $signTool sign /fd SHA256 /s My /sha1 $cert.Thumbprint $testPackage
if ($LASTEXITCODE -ne 0) { throw 'Test package signing failed.' }
$cert.Thumbprint
$cerPath
```

Record the thumbprint. In a separate **elevated** Windows PowerShell window,
import **that exact exported public certificate** into LocalMachine TrustedPeople
on the test machine (substitute its absolute path). This is explicit temporary
test-certificate trust, not a public signing setup:

```powershell
Import-Certificate -FilePath 'C:\path\to\build\msix-local-test\TriviaCountdown-local-test.cer' -CertStoreLocation 'Cert:\LocalMachine\TrustedPeople'
```

Return to the original, normal-user Windows PowerShell window:

```powershell
Add-AppxPackage -Path $testPackage
.\scripts\verify_windows_msix.ps1
```

The installed verifier launches the timed frozen render check through
`Invoke-CommandInDesktopPackage`, isolates system Python/FFmpeg from PATH, and
requires the application to report the exact installed MSIX identity via the
Windows package API. It leaves `STORE-003-*.json/.log` and `WIN-405-*.json` reports
under `build\verification\`, deleting synthetic videos. Its debugging activation
is supporting smoke evidence: also launch from **Start** and perform real GUI
checks, file dialogs, sample export, cancellation/overwrite/locked-output checks,
playback, DPI/icons, a version-changing update, and uninstall. Confirm your
Documents videos/CSVs/outputs survive update and uninstall. See the
[complete MSIX qualification checklist](../tasks/windows_store_qualification.md).

Uninstall the test package through Settings (or
`Get-AppxPackage -Name 'ColinWhite.TriviaCountdown' | Remove-AppxPackage`). After
testing, remove only the recorded temporary certificate thumbprint from
`Cert:\CurrentUser\My`; remove it from `Cert:\LocalMachine\TrustedPeople` in the
elevated window. Delete the local test-copy directory. No private key export,
repository secret, purchased certificate, or global security-control changes
are needed for this procedure. An expired test certificate requires a fresh
test-signed copy; do not upload the test-signed copy as the verified CI artifact.

### Certification and the first submission

Run the Windows App Certification Kit on the test-signed package on supported
Windows 10/11. Record its SDK/WACK version and full results, including any
desktop-app-specific warnings or certification follow-up. Passing MakeAppx or
the smoke verifier is not WACK approval.

Before certification submission, complete the shared source/license and
separate-machine approvals from the Windows preview qualification, plus the
MSIX-specific checklist. Publish durable matching FFmpeg sources/build
instructions for **every Store package version**, retaining older archives if
later builds change. A private workflow artifact or GitHub's automatic source
ZIP is insufficient for Store users. Record public source URL/hash alongside
each package version and provide source/license access in the listing materials.

In Partner Center, use existing **Submission 1**, complete pricing/availability,
properties (explain `runFullTrust` for the Python desktop GUI and bundled FFmpeg
subprocesses), age ratings, Store listings/screenshots, and privacy/support URLs.
Upload the original unsigned, verified CI MSIX under **Packages**. Record the
CI run, commit, hashes, source URLs, and submission ID. Microsoft signs the
distributed MSIX after certification; a public signing certificate is not
required for this Store route. Upload validation and certification are separate
results. The first submission remains manual; existing CLI automation checks
are read-only, and automated updates follow first publication.

## Future Signed Releases

A normal Gatekeeper launch requires Apple Developer Program membership, a Developer ID Application certificate, hardened-runtime signing, notarization with `notarytool`, and ticket stapling. Those steps are intentionally not part of this ad-hoc-signed prototype workflow.
